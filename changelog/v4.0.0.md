# Changelog - Version 4.0.0

This major release moves authorization into the daemon and hardens the trust boundary between clients and the trust store. Authorizing a binary is now an administrative action gated on the caller's OS identity, the daemon owns and writes its own trust store, and the dormant signed-upgrade path is hardened against four bypasses.

### Added
*   **Daemon-mediated `authorize` action**: The daemon now writes the trust store itself, as its own unprivileged user, instead of the client running `sudo keychain-auth authorize` and writing a root-owned file. New protocol action `authorize`; the daemon re-hashes the target and grants read, write, and search for the requested service.
*   **`admin_required` reason code**: Returned when an administrative action is requested by a peer that does not hold administrator rights. The CLI turns it into a clear "run with `sudo`" message.
*   **Superseded-hash ledger**: Hashes replaced by a signed upgrade are recorded and refused if replayed, as a rollback defence.
*   **Daemon started at install**: `install.sh` now starts the systemd unit after enabling it, so the daemon is immediately available to mediate authorization.

### Changed
*   **Authorization gated on OS identity**: The `authorize` action is no longer sufficient merely because the caller is the `keychain-auth` binary, since any process can execute that binary. On a system store the peer must be root (`sudo keychain-auth authorize`); on a user-mode store it must be the daemon's own user. Unknown credentials fail closed.
*   **Trust store owned by the daemon**: `/etc/keychain-auth/config.json` is `0600 keychain-auth:keychain-auth`, not `0644 root`. The daemon can read and write it, and it is not world-readable. Existing installs are corrected on the next install or setup run.
*   **`register` resets privileges on a hash change**: Re-registering a path with a new hash resets its service grants to Zero Trust instead of inheriting the old binary's access.
*   **Signed-upgrade path hardened**: A valid signature may only replace the hash of an already-registered path (upgrade-only), is verified over the same bytes that were hashed (no TOCTOU), must match the policy's service (no cross-service confusion), and cannot replay a superseded hash.
*   **Direct-write fallbacks keep the store daemon-owned**: `authorize`, `approve`, and `register` restore `keychain-auth:keychain-auth` `0600` after a privileged direct write.

### Fixed
*   **Self-authorization loophole**: A process running as the user could previously have used the daemon-mediated `authorize` path to authorize its own binary. Closed by the OS-identity gate.
*   **Privilege inheritance on re-registration**: `register` no longer carries old service grants across a hash change.
*   **Four signed-upgrade bypasses**: path binding, new-path grants, hash/signature TOCTOU, and rollback.
*   **Test-suite data race**: The handler mock keychain is now thread-safe, so concurrent batch writes no longer race.

### Security notes
*   **Re-authorization after an upgrade now requires `sudo`.** Authorizing a binary grants it service access, so it is an administrative action. This is a deliberate trade for closing the self-authorization loophole.
*   **Passwordless upgrades are not included.** Release signing (a `TrustedSigner`) was evaluated and deliberately not added: the signing key would become a global single point of compromise, with a larger blast radius than one `sudo` per upgrade. The dormant signature path was hardened instead. Full passwordless upgrades would require a signed manifest (path, version, hash), upgrade-only semantics, version-monotonic rollback protection, and an offline or HSM-held signing key.

### Compatibility
*   Backward compatible with clients pinned to 3.3.0. Clients that call `keychain-auth authorize` continue to work; on a system install the command must run under `sudo`.
*   `agentsecrets` should bump its `RequiredDaemonVersion` to 4.0.0 to pick up the hardened daemon.
